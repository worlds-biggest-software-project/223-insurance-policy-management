# Data Model Suggestion 2: Event-Sourced / Audit-First

> Project: Insurance Policy Management · Created: 2026-05-20

## Philosophy

This model treats every state change in the insurance lifecycle as an immutable event. Rather than storing "the current policy" as a mutable row, the system stores a sequence of events — PolicyQuoted, CoverageAdded, PolicyBound, EndorsementIssued, ClaimFiled, PaymentMade — and derives the current state by replaying or materialising those events. The event store is the single source of truth; read-optimised materialised views serve API queries.

Insurance is inherently event-driven: a policy's state is the cumulative result of transactions over time. Regulators routinely ask "what was the coverage on the date of loss?" or "show me every change to this policy since inception." In a traditional model, answering these questions requires history tables or audit logs bolted on after the fact. In an event-sourced model, temporal queries are native — you simply replay events up to the target date. This also aligns with ACORD transaction messages, which are themselves events (policy issuance, endorsement, cancellation).

The CQRS (Command Query Responsibility Segregation) pattern separates writes (events) from reads (materialised views). Write throughput is high because events are append-only. Read performance is high because materialised views are pre-computed. The trade-off is operational complexity: you must manage event schemas, projections, and eventual consistency.

**Best for:** Carriers requiring bulletproof audit trails, temporal queries ("what was true on date X?"), and AI/analytics workloads that benefit from a complete event history.

**Trade-offs:**
- Pro: Complete, immutable audit trail — every change is permanently recorded
- Pro: Natural temporal queries — replay to any point in time
- Pro: Perfect alignment with ACORD transaction messages (events = messages)
- Pro: Rich data for AI/ML — complete behavioral history for risk scoring and fraud detection
- Pro: High write throughput — append-only event store
- Con: Increased operational complexity (event schemas, projections, idempotency)
- Con: Eventual consistency between event store and materialised views
- Con: Event schema evolution requires careful versioning
- Con: Debugging requires understanding event replay, not just "reading the row"
- Con: Higher storage requirements (all events retained forever)

## Event Store (Source of Truth)

```sql
-- The immutable event store — all state changes recorded here
CREATE TABLE events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id UUID NOT NULL,
    stream_type VARCHAR(50) NOT NULL,         -- 'policy', 'claim', 'billing', 'party', 'underwriting'
    stream_id UUID NOT NULL,                  -- Aggregate ID (policy_id, claim_id, etc.)
    event_type VARCHAR(100) NOT NULL,         -- e.g., 'PolicyQuoted', 'CoverageAdded', 'ClaimFiled'
    event_version INT NOT NULL,               -- Per-stream sequence number
    payload JSONB NOT NULL,                   -- Event-specific data
    metadata JSONB NOT NULL DEFAULT '{}',     -- Correlation IDs, causation, user context
    created_by UUID,                          -- User who triggered the event
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (stream_id, event_version)         -- Optimistic concurrency control
);

-- Append-only: no UPDATE or DELETE allowed (enforce via RLS or application)

CREATE INDEX idx_events_stream ON events(stream_id, event_version);
CREATE INDEX idx_events_tenant_type ON events(tenant_id, stream_type, created_at);
CREATE INDEX idx_events_type ON events(event_type, created_at);
CREATE INDEX idx_events_created ON events(tenant_id, created_at);

-- GIN index for querying within event payloads
CREATE INDEX idx_events_payload ON events USING gin(payload jsonb_path_ops);
```

## Materialised Read Models (CQRS Query Side)

These tables are projections — derived from events, rebuildable at any time.

```sql
-- Current policy state (materialised from PolicyQuoted + PolicyBound + EndorsementProcessed + ... events)
CREATE TABLE mv_policies (
    id UUID PRIMARY KEY,                      -- Same as stream_id
    tenant_id UUID NOT NULL,
    policy_number VARCHAR(50) NOT NULL,
    product_code VARCHAR(50) NOT NULL,
    line_of_business VARCHAR(50) NOT NULL,
    policyholder_id UUID NOT NULL,
    agent_id UUID,
    status VARCHAR(30) NOT NULL,
    effective_date DATE NOT NULL,
    expiration_date DATE NOT NULL,
    jurisdiction CHAR(2) NOT NULL,
    total_premium NUMERIC(15,2),
    currency CHAR(3) NOT NULL DEFAULT 'USD',
    last_endorsement_number INT NOT NULL DEFAULT 0,
    last_event_version INT NOT NULL,          -- Tracks which events have been projected
    created_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,
    UNIQUE (tenant_id, policy_number)
);

CREATE INDEX idx_mv_policies_tenant_status ON mv_policies(tenant_id, status);
CREATE INDEX idx_mv_policies_policyholder ON mv_policies(policyholder_id);
CREATE INDEX idx_mv_policies_dates ON mv_policies(effective_date, expiration_date);

-- Current policy coverages (materialised)
CREATE TABLE mv_policy_coverages (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    policy_id UUID NOT NULL REFERENCES mv_policies(id),
    coverage_code VARCHAR(50) NOT NULL,
    coverage_name VARCHAR(255) NOT NULL,
    coverage_limit NUMERIC(15,2) NOT NULL,
    deductible NUMERIC(15,2) NOT NULL DEFAULT 0,
    premium NUMERIC(15,2) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'active',
    updated_at TIMESTAMPTZ NOT NULL
);

CREATE INDEX idx_mv_policy_coverages_policy ON mv_policy_coverages(policy_id);

-- Current claim state (materialised from ClaimFiled + ReserveSet + PaymentMade + ... events)
CREATE TABLE mv_claims (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    claim_number VARCHAR(50) NOT NULL,
    policy_id UUID NOT NULL,
    claimant_id UUID NOT NULL,
    status VARCHAR(30) NOT NULL,
    loss_date DATE NOT NULL,
    reported_date DATE NOT NULL,
    loss_type VARCHAR(50) NOT NULL,
    loss_description TEXT,
    assigned_adjuster_id UUID,
    total_incurred NUMERIC(15,2) NOT NULL DEFAULT 0,
    total_paid NUMERIC(15,2) NOT NULL DEFAULT 0,
    total_reserved NUMERIC(15,2) NOT NULL DEFAULT 0,
    fraud_score NUMERIC(5,2),
    last_event_version INT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL,
    UNIQUE (tenant_id, claim_number)
);

CREATE INDEX idx_mv_claims_policy ON mv_claims(policy_id);
CREATE INDEX idx_mv_claims_tenant_status ON mv_claims(tenant_id, status);
CREATE INDEX idx_mv_claims_loss_date ON mv_claims(loss_date);

-- Current billing state (materialised)
CREATE TABLE mv_billing_accounts (
    id UUID PRIMARY KEY,

    account_number VARCHAR(50) NOT NULL,
```

## Projection Management

```sql
-- Tracks projection state for each materialised view
CREATE TABLE projections (
    projection_name VARCHAR(100) PRIMARY KEY,  -- e.g., 'mv_policies', 'mv_claims'
    last_processed_event_id UUID,
    last_processed_at TIMESTAMPTZ,
    status VARCHAR(20) NOT NULL DEFAULT 'running',  -- 'running', 'paused', 'rebuilding', 'error'
    error_message TEXT,
    events_per_second NUMERIC(10,2),
    updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Dead letter queue for events that fail projection
CREATE TABLE projection_failures (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    projection_name VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL REFERENCES events(id),
    error_message TEXT NOT NULL,
    retry_count INT NOT NULL DEFAULT 0,
    max_retries INT NOT NULL DEFAULT 5,
    next_retry_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_projection_failures_retry ON projection_failures(next_retry_at) WHERE retry_count < max_retries;
```

## Snapshots (Performance Optimisation)

```sql
-- Periodic snapshots to avoid replaying entire event streams
CREATE TABLE snapshots (
    stream_id UUID NOT NULL,
    stream_type VARCHAR(50) NOT NULL,
    event_version INT NOT NULL,               -- Snapshot taken at this version
    state JSONB NOT NULL,                     -- Full aggregate state at this point
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (stream_id, event_version)
);

-- Snapshot every 50 events per stream for performance
-- To rebuild current state: load latest snapshot + replay events since snapshot version
```

```sql
-- Command queue for async processing (optional — can also be synchronous)
CREATE TABLE commands (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    command_type VARCHAR(100) NOT NULL,        -- 'QuotePolicy', 'BindPolicy', 'FileClaim', 'ProcessPayment'
```

## Temporal Query Examples

```sql
-- "What was the policy state on the date of loss?"
-- Replay events up to the loss date
SELECT payload
FROM events
WHERE stream_id = :policy_id
  AND stream_type = 'policy'
  AND created_at <= :loss_date
ORDER BY event_version ASC;

-- "Show all changes to this policy since inception"
SELECT event_type, payload, created_by, created_at
FROM events
WHERE stream_id = :policy_id
  AND stream_type = 'policy'
ORDER BY event_version ASC;

-- "What premium was in effect on 2026-09-15?"
-- Find the latest PremiumCalculated event before that date
SELECT payload->>'total_premium' AS premium_at_date
FROM events
WHERE stream_id = :policy_id
  AND event_type IN ('PolicyQuoted', 'PolicyBound', 'EndorsementProcessed')
  AND created_at <= '2026-09-15'
ORDER BY event_version DESC
LIMIT 1;

-- "Find all policies where coverage was modified in the last 30 days"
SELECT DISTINCT stream_id
FROM events
WHERE tenant_id = :tenant_id
  AND event_type = 'EndorsementProcessed'
  AND created_at >= now() - INTERVAL '30 days';

-- "Build fraud detection training data from claim event sequences"
SELECT stream_id AS claim_id,
       jsonb_agg(
           jsonb_build_object('event', event_type, 'time', created_at, 'data', payload)
           ORDER BY event_version
       ) AS event_sequence
FROM events
WHERE tenant_id = :tenant_id
  AND stream_type = 'claim'
GROUP BY stream_id;
```

## Key Design Decisions

1. **Single event table, not per-aggregate** — all events go into one `events` table partitioned logically by `stream_type`. This simplifies infrastructure (one table to back up, replicate, index) while still allowing per-aggregate replay via `stream_id`. For very high volumes, PostgreSQL table partitioning by `created_at` can be added.

2. **Optimistic concurrency via stream versioning** — the `UNIQUE (stream_id, event_version)` constraint prevents concurrent writes to the same aggregate. If two commands try to write version 5, one fails and retries after re-reading the stream. This replaces row-level locking.

3. **Materialised views are disposable** — all `mv_*` tables can be dropped and rebuilt from the event store. This means schema changes to read models are non-destructive: add a column, rebuild, done. No data migrations needed.

4. **Snapshots every ~50 events** — for aggregates with long histories (policies with many endorsements over years), snapshots prevent expensive full replays. Load the latest snapshot, then replay only events since the snapshot.

5. **Event payloads carry full context** — each event payload includes enough data to understand the event independently (e.g., PolicyQuoted includes all coverages, not just a coverage ID). This makes events self-describing for analytics and debugging, at the cost of some data duplication.

6. **ACORD transaction messages map to events** — an ACORD XML policy issuance message is essentially a PolicyIssued event. Import/export is a matter of transforming between ACORD XML and event payloads, which is more natural than mapping XML to normalised tables.

7. **AI/ML-native design** — the event store provides complete behavioural sequences (all actions on a claim, all changes to a policy) that are ideal training data for fraud detection, risk scoring, and lapse prediction models. No ETL needed — query the event store directly.

8. **Idempotency via command keys** — the `commands` table uses `idempotency_key` to prevent duplicate processing when retrying failed commands. Critical for payment processing and claim payments.

9. **Reference data is not event-sourced** — tenants, users, and products change infrequently and are managed via traditional CRUD. Over-engineering these as event-sourced adds complexity without benefit.

10. **Projection failure handling** — the `projection_failures` dead letter queue captures events that fail to project, with configurable retry. This prevents a single bad event from halting the entire projection pipeline.
